# CLAUDE.md — operating rules for agents working in codeaster-en

You are working in **codeaster-en**, an English overlay for the code_aster finite element solver. Read this file fully before doing anything. It is short on purpose; the detail is in `docs/`.

## 1. What this repo is

- An **overlay**, not a fork. The solver source is a pinned git submodule at `upstream/` (a GitHub mirror of `gitlab.com/codeaster/src`). We never edit it.
- The overlay = `en/` (translations and references), `tools/` (Python package `codeaster_en`, CLI `caen`), `tests/`, `docs/`.
- End goal: an English-first layer that lets ClearFEA (and any engineer or LLM) drive code_aster and read its results and diagnostics in English. See `docs/CLEARFEA-INTEGRATION.md`.

## 2. Hard rules — never break these

1. **Do not modify anything under `upstream/`.** Not a comment, not a filename. If something there must change, write it up in `docs/DECISIONS.md` as a proposed upstream contribution instead.
2. **French command and keyword names stay French.** `AFFE_MODELE`, `GROUP_MA`, `PRES_REP` are the solver's API. We annotate and explain; we never rename, alias or "englishify" identifiers in any generated `.comm` file, catalog, or example.
3. **The glossary (`en/glossary.yaml`) is law.** If a term has an entry, use that English. If it doesn't and you need one, add the entry in the same PR with `status: proposed`. Never translate the same term two ways.
4. **Preserve message placeholders exactly.** `%(k1)s`, `%(i1)d`, `%(r1)f`, `%(r1)12.5E` etc. must appear in the English message with identical names and formats. The validator (`caen validate`) enforces this; run it.
5. **Provenance on everything.** Every English artefact records: upstream commit/tag, source file + line or doc ID (e.g. `U4.41.01`), translation method (`machine` / `assisted` / `reviewed`), reviewer and date if reviewed.
6. **Never invent solver behaviour.** Describe a keyword only from the catalog definition, the official doc, or a test case under `upstream/astest/`. Cite which. If unsure, write `TODO(verify)` and say why.
7. **Scope is `docs/COMMAND-SET.md`.** Do not translate commands, messages or docs outside the current tier unless the task says so.
8. **Do not build the solver in a session.** It takes hours and needs system prerequisites. Runtime tests use committed fixtures in `tests/fixtures/` (generated by the `solver-fixtures` GitHub Action with the official docker image) — see `docs/ARCHITECTURE.md` §6.
9. **Network.** The sandbox usually cannot reach gitlab.com or code-aster.org. Everything you need is in `upstream/` (via GitHub) or attached by the owner. Do not try to work around a blocked site.
10. **Licensing.** Everything you write here is GPL-3.0-or-later. Translated docs keep the EDF R&D attribution header and original doc ID. See `docs/LICENSING.md`.

## 3. How work is organised

- `docs/PLAN.md` — phases → tasks with acceptance criteria. Tasks are session-sized (one to three hours of agent work).
- `docs/PROGRESS.md` — living log. **Read it first, update it last.** One entry per session: task ID, what was done, what's open, decisions taken.
- `docs/DECISIONS.md` — ADR-style log. Any choice that constrains future work goes here, not in chat.
- `docs/SESSION-PROMPTS.md` — the prompts the owner uses to start sessions. If you find yourself needing context that isn't there, add it there.

### Session routine

1. Read `docs/PROGRESS.md` (last 3 entries) and the task you've been given in `docs/PLAN.md`.
2. Check out a branch `task/<phase>-<id>-<slug>` from `main`.
3. Do the task. Keep PRs single-purpose. Prefer many small commits with conventional messages (`feat(messages): …`, `docs(commands): …`, `tools(extract): …`).
4. Run `ruff check`, `ruff format`, `pytest`, `caen validate` before finishing.
5. Append the PROGRESS entry. Open the PR with: what changed, how it was verified, anything the owner must review by hand (translations needing an engineer's eye are flagged `needs-engineer-review`).
6. Stop. Don't start the next task in the same session unless told to.

### When to stop and ask

- A task needs a file or PDF that isn't in the repo.
- A translation choice would change the glossary meaning of a term already marked `reviewed`.
- You'd need to touch `upstream/`.
- The upstream structure differs from what `docs/ARCHITECTURE.md` §3 assumes (paths moved, catalog format changed). Record what you found in PROGRESS and ask before adapting the tooling.

## 5. Conventions

- Python ≥ 3.11, `src`-less layout under `tools/codeaster_en`, typed, `ruff` for lint+format, `pytest`.
- Data files: YAML for human-edited (glossary), JSON for generated (catalog, messages). Generated files carry a header `"_generated_from": {...}` and are never hand-edited — change the extractor instead.
- English style: plain engineering English, British or American consistently per file (we use **American**), SI unit names, no marketing tone. "Element" not "cell", "node" not "vertex", "load case" not "charge".
- Markdown: one H1, ATX headings, fenced code with language, tables for keyword lists.
- Commit messages: Conventional Commits. Scopes: `glossary`, `commands`, `messages`, `docs`, `extract`, `validate`, `mess`, `report`, `comm`, `ci`, `fixtures`.

## 6. Where the French actually is (so you know where to look)

| Layer in upstream | Language | Our action |
|---|---|---|
| `code_aster/Cata/Commands/*.py` — command catalogs (one file per command; keyword names, types, defaults, `fr=` help strings) | French identifiers + French help | Extract → annotate in English (`en/commands/`) |
| `code_aster/Messages/*.py` — `cata_msg` dicts, one file per message family | French text | Translate (`en/messages/`) |
| `astest/*.comm` + `*.export` — ~3800 test cases | French keywords, French comments | Index only; use as examples |
| `bibfor/`, `bibc/`, `bibcxx/` — Fortran/C/C++ solver | French comments and names | **Ignore.** Out of scope forever. |
| `catalo/` — element/option catalogs | French | Ignore unless a command reference needs an element name explained |
| Official docs (PDF, not in repo) — U1 usage, U4 command reference, R theory, V validation | French (+ machine English) | Translate U4 for in-scope commands; curate a short engineers' guide |
| Solver output `.mess` (log), `.resu`, tables | French | Parse and render in English at runtime |
| Results `.rmed` / `.med` | Binary (MED/HDF5), field names French (`DEPL`, `SIEQ_NOEU`) | Read; label in English via glossary |

Verify the paths above against the pinned `upstream/` in your first session (Phase 0, task 0.4) and correct this table if they differ.
