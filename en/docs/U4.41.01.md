# AFFE_MODELE operator

## 1 Purpose

Define the physics modeled (mechanical, thermal or acoustic) and the type of finite elements.

This operator assigns modeling types to all or part of the mesh, which defines:

- the degrees of freedom on the nodes (and the associated conservation equation or equations),
- the finite element types on the elements,

The finite elements that can be chosen are described in the [U3] fascicles.

The element types are described in the document « Description du fichier de maillage de code_aster » [U3.01.00].

This operator also defines how the finite elements are distributed for parallel elementary calculations and assemblies.

Produces a data structure of type `modele`.

## 3 Operands

### 3.1 Operand MAILLAGE

```text
♦     MAILLAGE = ma
```

Name of the mesh of the study, to which the finite elements are assigned.

Note: for axisymmetric modeling types, the axis of revolution is the Y axis of the mesh. The whole structure must be meshed in X≥0 . The Ox axis is therefore the radial direction. The components of the computed fields are therefore: X for the radial direction, Y for the axial direction, Z for the orthoradial (circumferential) direction.

### 3.2 Keyword AFFE

```text
♦     |     AFFE
```

Defines the finite element types assigned to the chosen mesh entities. Each occurrence gives one modeling type.

Note: remember that Code_Aster applies the overwrite rule (cf. § 3.4 [ U1.03.00 ]):

- assignments are made by superposing the effects of the different keywords,
- in case of conflict, the last keyword given wins over the earlier ones.

The mesh entities are given by the operands:

| Operands | Content / meaning |
|---|---|
| TOUT = 'OUI' | Assignment to all the elements |
| GROUP_MA = g_mail | Assignment to a list of element groups |

The finite element type is given by the operands:

| Operands | Content / meaning |
|---|---|
| PHENOMENE | Physics modeled (associated conservation equation) |
| MODELISATION | Type of interpolation and discretization |
| FORMULATION | Type of formulation, in some cases |

#### 3.2.1 Operands PHENOMENE, MODELISATION and FORMULATION

```text
♦     PHENOMENE
♦     MODELISATION
◊     FORMULATION
```

The first two keywords, PHENOMENE and MODELISATION, are mandatory in each occurrence of the factor keyword AFFE. This pair of keywords defines one-to-one the element type assigned to an element shape.

In some cases, the FORMULATION used may have to be given:

- For HHO discretizations (3D_HHO, AXIS_HHO or D_PLAN_HHO), it says whether the approach is linear ( FORMULATION='LINEAIRE' ) or quadratic ( FORMULATION='QUADRATIQUE' );
- For fluid or fluid-structure interaction discretizations, it says whether the formulation has three variables (U,P,ϕ) or two variables (U,P) or (U,ψ), see the documentation [R4.02.02].
- For second-gradient modeling types in mechanics, it says whether the original formulation of the second-gradient model is used (FORMULATION='DIL') or the incompressible one (FORMULATION='DIL_INCO').

<!-- page 5 -->

Note: the keyword PHENOMENE must have the same value in all the occurrences of the factor keyword AFFE .

Note: when finite elements are assigned to the volume (and/or surface) elements of the element group g_mail , and this group also contains the boundary (and/or edge) elements of those volume (and/or surface) elements, Code_Aster automatically assigns to the latter the finite elements needed by some calculation options (application of external loads, for example). If additional modeling types must be assigned to these interfaces, the mesh must provide duplicated elements: this is the case, for example, in fluid-structure interaction.

### 3.3 Keyword AFFE_SOUS_STRUC

```text
♦     |     AFFE_SOUS_STRUC
```

Can be used only for a model that uses static substructures [U1.01.04].

```text
♦     /     SUPER_MAILLE = l_mail
```

l_mail is the list of super-elements to assign in the model. As for finite elements, it is not mandatory to assign all the elements of the mesh. AFFE_MODELE confirms which substructures are used in the model. The difference with classic finite elements is that on super-elements neither the MODELISATION nor the PHENOMENE is chosen, because the macro-element (built by the operator MACR_ELEM_STAT [U4.62.01]) assigned to the super-element has its own modeling type and its own physics (those used to compute it).

Warning! Your model must contain at least one finite element (keyword AFFE in §3.2) when you use static substructures defined from a physical mesh (read by LIRE_MAILLAGE ), because it is not possible to have only macro-elements in that case.

```text
/     TOUT = 'OUI'
```

All the (super) elements are assigned.

### 3.4 Operand VERI_JACOBIEN

```text
◊     VERI_JACOBIEN = 'OUI' / 'NON'
```

This keyword checks that the elements of the model are not too distorted. The Jacobian of the geometric transformation that maps the reference element onto each real element of the model is computed. If the Jacobian changes sign over the integration points of an element, that element is very badly shaped. A warning is then issued.

### 3.5 Operand VERI_NORM_IFS

```text
◊     VERI_NORM_IFS = 'OUI' / 'NON'
```

This keyword checks that all the normals on the fluid-structure interfaces (FLUI_STRU modeling) point the same way. If not, a warning is issued and the user is asked to reorient these normals, either in the mesh directly or with the operator MODI_MAILLAGE (keywords ORIE_PEAU_2D and ORIE_PEAU_3D for example).

### 3.7 Keyword DISTRIBUTION

```text
◊     DISTRIBUTION = _F( METHODE = methode, … )
```

This keyword distributes the finite elements of the model for the parallelism of the elementary calculations, the assemblies and some linear solvers. Cf. [U2.08.06] « Notice d'utilisation du parallélisme ».

It defines how the elements are distributed (or not) for the parallel phases of Code_Aster. The user can thus control this distribution among the processors.

<!-- page 11 -->

Parallelism acts:

- on the elementary calculations and on the assembly of matrices and vectors (this is what the factor keyword DISTRIBUTION controls),
- in the solution of the linear system if the solver is parallel (cf. [U4.50.01]).

With the new parallel mode (parallel mesh of type `maillage_p`), the distribution mode must be CENTRALISE, because the mesh has already been distributed and the calculations cannot be distributed again. If another distribution mode is chosen for this parallel mode, it is switched to CENTRALISE automatically without telling the user.

Note: the distribution mode can be changed during a study with the command MODI_MODELE [U4.41.02].

Note: it can be handy to continue a parallel calculation with a number of processors different from the one used for the initial calculation. In particular, one may want to run some post-processing sequentially. The command MODI_MODELE is recommended to define the distribution to use in the continuation. More precisely, when the initial calculation used parallelism "by element groups" ( ' GROUP_ELEM ' or ' SOUS_DOMAINE ' ), the command MODI_MODELE is not needed. On the other hand, when the initial calculation used parallelism "by elements" ( 'MAIL_CONTIGU' or 'MAIL_DISPERSE' ), the command MODI_MODELE is mandatory. If it is forgotten, the calculation stops with an error message.

### 3.8 Keyword METHODE

##### 3.8.1.1 METHODE = / 'CENTRALISE'

Parallelism starts only at the linear solver. Each processor builds the whole system to solve and gives it to the solver. Elementary calculations are not parallel. This distribution method is mandatory for a parallel mesh of type `maillage_p`.

##### 3.8.1.2 METHODE = / 'GROUP_ELEM'

This distribution mode gives a perfect a priori load balance (in number of elementary calculations): for a given element type, each processor does the same number of elementary calculations (give or take one). Of course this says nothing about the final load balance, in particular in nonlinear calculations, where the cost of an elementary calculation depends on parameters other than the element type. In this mode, the elements of the model are gathered in « groups » to share some calculations, which improves efficiency. The number of elements per group can be chosen in the command DEBUT [U4.11.01]. This is also the only mode able to distribute the elementary calculations induced by late elements, that is by loads such as boundary conditions with Lagrange-multiplier enforcement or continuous contact.

##### 3.8.1.3 METHODE = / 'MAIL_DISPERSE'

The distribution acts on the elements. They are shared out evenly among the available processors, the way cards are dealt to several players. This is also called « cyclic » distribution.

For example, with a model of 8 elements run on 4 processors, the distribution is:

| Distribution mode | Element 1 | Element 2 | Element 3 | Element 4 | Element 5 | Element 6 | Element 7 | Element 8 |
|---|---|---|---|---|---|---|---|---|
| MAIL_DISPERSE | Proc. 0 | Proc. 1 | Proc. 2 | Proc. 3 | Proc. 0 | Proc. 1 | Proc. 2 | Proc. 3 |

With this distribution mode, a processor handles elements regularly spaced in the element order of the mesh. The advantage is that « statistically » each processor handles as many hexahedra, pentahedra, …, and triangles.

<!-- page 12 -->

The workload of the elementary calculations is usually well balanced. On the other hand, the matrix assembled on a processor is very « scattered », the opposite of the 'MAIL_CONTIGU' mode.

##### 3.8.1.4 METHODE = /'MAIL_CONTIGU'

The distribution acts on the elements. They are shared out in packets of contiguous elements among the available processors.

For example, with a model of 8 elements and a machine with 4 available processors, the distribution is:

| Distribution mode | Element 1 | Element 2 | Element 3 | Element 4 | Element 5 | Element 6 | Element 7 | Element 8 |
|---|---|---|---|---|---|---|---|---|
| MAIL_CONTIGU | Proc. 0 | Proc. 0 | Proc. 1 | Proc. 1 | Proc. 2 | Proc. 2 | Proc. 3 | Proc. 3 |

With this distribution mode, the workload of the elementary calculations can be less balanced. For example, a processor may have only « easy » boundary elements to handle. On the other hand, the matrix assembled on a processor is usually more compact.

##### 3.8.1.5 Keyword CHARGE_PROC0_MA

```text
◊ CHARGE_PROC0_MA = / 100 [DEFAUT]
                    / pct
```

This keyword is available only for the distribution modes 'MAIL_DISPERSE' and 'MAIL_CONTIGU'. These modes usually do not share the workload evenly because of the boundary conditions with Lagrange-multiplier enforcement, whose elementary calculations are handled by processor 0.

To relieve processor 0 (or on the contrary to give it more work), use the keyword CHARGE_PROC0_MA. It lets the user choose the percentage of the workload given to processor 0.

For example, if the user chooses CHARGE_PROC0_MA = 80, processor 0 handles 20% fewer elements than the other processors, that is 80% of the workload it would carry if the sharing were even.

##### 3.8.1.6 METHODE = / 'SOUS_DOMAINE' [DEFAULT]

This distribution of the elements relies on a decomposition of the mesh into subdomains, built by an external partitioning tool given by the keyword PARTITIONNEUR:

```text
◊PARTITION NEUR               =  / 'METIS'            [DEFAULT ]
                                                / 'SCOTCH'
```

The user can set the number of subdomains with the keyword NB_SOUS_DOMAINE:

```text
◊NB_SOUS_DOMAINE         =          / nbproc          [DEFAULT ]
                                                      / nb_sous_dom
```

By default, the number of subdomains equals the number of processors in the calculation ( nbproc ).

The finite elements of the model carried by the elements of each subdomain are then distributed by groups of similar elements (as in the distribution of the GROUP_ELEM method), to balance the elementary calculations as well as possible. Partitioning the mesh into subdomains first ensures that all the elements of a finite element group belong to a single subdomain.

## 4 Execution phase

From the keywords PHENOMENE, MODELISATION and FORMULATION, a data structure is created that gives the element type attached to each element.

A short summary of the assignments is always printed (INFO=1) in the message file.

## 5 Example

For a modeling of the 'MECANIQUE' physics, 3D isoparametric finite elements are assigned to the element group gma of the mesh ma. If the element group gma also contains the boundary and/or edge elements of the volume elements, the isoparametric finite elements needed by some calculation options (application of external loads, for example, cf. [U4.44.01]) are assigned to them as well.

```text
mo    = AFFE_MODELE     (     MAILLAGE =  ma,
                              AFFE  = (   _F(   GROUP_MA    =     gma,
                                                PHENOMENE   =     'MECANIQUE',
                                                MODELISATION      =     '3D'  ),
                                          ) )
```
