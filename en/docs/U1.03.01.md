# Supervisor and command language

Summary:

This document describes the role and operation:

- of the supervisor, which drives a Code_Aster run;
- and of the command language, which carries the communication between the user and the code.

<!-- page 2 -->

Table of Contents

<!-- page 3 -->

The role of the supervisor is to command the sequence of operations while a program runs. The run instructions are generally given by the user. This needs a formal way for the code and its user to communicate: the command language.

The Python language is used to write the command catalog, the supervisor and the user command files. For the command files, this relieves the supervisor of the task of syntax analysis, which is left to Python itself.

A command file is a sequence of calls to Python functions (the commands), defined in the command catalog. These functions have input arguments, the keywords and their content, and output arguments, the produced concepts. The user who writes a command file must therefore follow the general syntax of Python (parentheses, indentation…) and the rules imposed by the command catalog (the arguments given are consistent with what the function expects).

For a first contact with the code, the reader may skip chapter 2.

## 2 General mechanism of the supervisor

### 2.1 General architecture

The basic elements involved in an Aster calculation run are:

- the command file, given by the user,
- the command catalog: a Python module named `cata` placed in the package `Cata`,
- the high-level object SUPERVISEUR,
- the object JDC created by the latter, which is finally executed.

The object SUPERVISEUR is a Python object that analyzes the options passed on the command line, imports the command catalog, creates the object JDC from the command file and executes it.

The object JDC (for «Jeu De Commandes», command set) is a Python object created by the object SUPERVISEUR from the text of the command file and from the command catalog module. It contains the objects ETAPE. The object JDC represents the user command file.

The objects ETAPE represent each call to an Aster command in the command file. Each object ETAPE carries the name of the command it refers to, the list of active keywords and their values, and the type and name of the produced concept.

Building then executing the object JDC triggers the following actions:

- syntax analysis of the user command file: this is the level where the Python syntax is checked (parentheses, commas between keywords, indentation…). Detecting an error (Python SyntaxError) stops the Aster run. The first error is fatal: the following errors are not searched for,
- construction of the steps: an object ETAPE is created for each call to an Aster command in the command file. This object is registered with JDC, which manages the list of steps and the related concepts,
- check of each ETAPE: if the call to a command in the user file is inconsistent with the command catalog, a report is printed and the run is stopped at this level. This is the semantic check,
- actual execution of the commands: for each step, in order, a call to the corresponding high-level FORTRAN routine (op0nnn.f).

### 2.2 Global or step-by-step execution

A command set can be built and executed in two modes:

- the global mode, in which all the steps of the command set are first built and then executed in their order of appearance. This mode is chosen by the keyword PAR_LOT=’OUI’ in the start command DEBUT,
- the step-by-step mode, in which each step is executed immediately after it is built. This mode is chosen by the keyword PAR_LOT=’NON’ in the command DEBUT.

If the user gives nothing in the start command, the global mode (PAR_LOT=’OUI’) is used. Each of these two modes has its advantages and drawbacks.

The global execution mode guarantees the user that the whole file is semantically correct before starting calculations that could fail or not converge. It would indeed be a pity to stop on a fatal error after a long solution because of a keyword forgotten in a post-processing command. It also means that all the steps of the command set are built and kept in memory. With several thousand steps, this can use a lot of memory, and this mode is then no longer advised.

The step-by-step mode builds a step only after executing the previous one. It therefore detects only the semantic errors of the current command, and has the drawback described above. It does, however, allow a computed result (in a result object) to be used in the command file, for example to place conditional instructions there. In this mode, the executed step is immediately freed from memory. The memory used is then independent of the number of steps to execute.

Here is an example of a loop with a stop criterion on the value of a computed quantity, stored in the result object of type table: RELV[k]. If, for example, a mandatory keyword is missing in the call to POST_RELEVE_T, this will be detected only after the complete execution of the first MECA_STATIQUE. On the other hand, the step-by-step mode makes the assignment of the variable SYY possible here, since the result object RELV[k] has been completely computed when the supervisor executes this line.

```text
DEBUT(PAR_LOT='NON')
RESU=[None]*10
RELV=[None]*10
for k in range(1,10):
   RESU[k]=MECA_STATIQUE( ... )
   RELV[k]=POST_RELEVE_T( ... )
   SYY=RELV[k]['VMIS',4]
   if SYY < critere :
     break
FIN()
```

Note that the choice of an execution mode determines the order in which the semantic analysis takes place (ETAPE by ETAPE, or globally for the whole JDC). But in both cases the Python syntax analysis is always done first for the whole command file.

Remark:

EFICAS can generate and read back only command sets that contain ASTER commands exclusively, without other Python instructions; this regardless of the PAR_LOT mode chosen.

### 2.3 Construction of the steps

When each object ETAPE is built, its semantic consistency with the catalog of the command it refers to is checked. Any error detected is recorded in a report which, in global execution mode, is delivered after the analysis of the whole command file.

Examples of semantic checks:

- the number of arguments of the keywords is respected,
- the type of argument is respected,
- an argument belongs to a list of allowed values,
- the spelling of a keyword or a factor keyword is exact,
- the exclusion or implication rules between keywords are respected,
- the mandatory keywords are present.

At this stage, if the command is an operator and produces a concept, the concept is typed. The supervisor checks that a concept of the same name has not already been defined or, if it is reused, that the command allows it.

### 2.4 Processing of macro-commands

A macro-command, as seen by the user, is an ordinary command. In fact, it does not call a high-level Fortran routine directly but generates other commands.

There are two types of macro-commands:

- the Python macros,
- the supervisor macros: these are the special commands (DEBUT, FORMULE, INCLUDE, INCLUDE_MATERIAU, POURSUITE) that need processing when they are built.

Like the JDC itself, the call to a macro-command produces a parent object (of type MACRO-ETAPE) that contains child objects: the steps that the macro generates, or even other macros.

A macro-command of the JDC is first processed like the other commands (syntax check, construction of the macro step). Then it is «built» by applying the Python method Build to the object JDC. After its construction, the steps of the commands produced by the macro replace the step of the macro itself, for later execution.

It is important to note that the construction phase of the macro-commands takes place just before their execution, and not during the global pass over the command file in mode PAR_LOT=’OUI’. This has two consequences:

- EFICAS analyzes the syntax of the macro-command itself, but not that of its sub-commands.
- On the other hand, the programming of macros can use data computed earlier and brought back into the Python namespace, without having to impose the mode PAR_LOT=’NON’ on the user of the macro.

### 2.5 The start procedures

The available start procedures are:

DEBUT (see [U4.11.01] and POURSUITE [U4.11.03])

At least one of these two procedures must be present in the command file. No other Aster command may precede them. If one does, or if neither is present, the run is stopped as soon as the JDC is created. These procedures hold the information on the execution mode (PAR_LOT=’OUI’ or ‘NON’) that sets the execution mode of the commands that follow.

They are supervisor macro-commands that, when built, call the Fortran routines that initialize the calculation with the following tasks:

<!-- page 6 -->

- "connection" of the logical units of the standard files,
- opening of the databases,
- reading of the element catalog.

The first task maps the logical units of the standard input/output files (message, error, result).

The second task defines and opens the databases (direct-access files used by the memory manager) according to the instructions of the user, who can redefine parameters of these files (see documents [U4.11.01] and [U4.11.03] on the start procedures). For this, the JEVEUX initialization routines are called (see document [D6.02.01], the memory manager JEVEUX).

The sequence of commands to execute must end with the command FIN. The text that follows FIN must be commented out (that is, start with #). For an included file, the command RETOUR marks the end of the instructions that ASTER must take into account.

Remark:

In interactive mode, with commands typed by hand, do not put a command FIN, and pass the argument –interact on the command line that submits the job.

### 2.6 Links with EFICAS

The core of the supervisor is shared with Eficas, the editor of Aster command files. When a command file is edited, Eficas performs the syntax analysis and the consistency checks of the result objects by building the JDC and its objects ETAPE. Eficas of course does not perform the construction of the macro-commands, which would need the Aster source code.

## 3 The command language

### 3.1 Python and the command language

A command file for Code_Aster is made exclusively of Python instructions. The first constraint is therefore to follow the rules of this language. The Python tutorial (www.python.org) or the many introductory books on Python can be read for more detail, but this is not necessary to use Aster.

A command file can contain Python instructions of two kinds: Aster commands and… any other Python instruction. Indeed, a command file is a Python program in its own right, and in particular control structures (loops), tests (if), numerical calculations and calls to pre- and post-processing functions can be placed in it.

For a «classical» use of the code, where the command file contains exclusively Aster commands, the two Python-specific rules to remember are:

- No indentation on the first line of the declaration of an instruction.

```text
mail = LIRE_MAILLAGE ( )
```

Neither a blank nor a tab may be placed before the character string `mail`.

- The arguments of the functions, in other words the keywords of the commands, are separated by commas; they consist of a keyword, the sign «=», and the content of the keyword.

Important:

The editor EFICAS can produce only command files of this type: containing exclusively ASTER commands, without other Python instructions. Using EFICAS essentially guarantees three things:

<!-- page 7 -->

- the file produced will have a correct Python syntax,
- the commands produced will be consistent with the command catalog,
- the result objects produced will be correctly chained (no use of a result object before it has been created by a previous command).

A user who has written a command file this way is protected from a stop at run time because of a syntax problem.

### 3.2 Notion of result object (concept)

Definition: a result object (concept) is an Aster data structure that the user can handle and name. These result objects are typed when they are created and can be used only as an input argument of the corresponding type in a later command.

The notion of result object therefore lets the user handle objects symbolically and independently of their internal representation (which the user may not know). Moreover, the Python object designated by the name of the result object holds no information other than its type, its class in the Python sense (see doc D). Its name, passed by the supervisor to the FORTRAN, lets Aster find the corresponding data structure in the global database. But the data structure cannot be seen from the command file. For example, the following instructions do not print the data structure of type mesh named `mail`:

```text
mail=LIRE_MAILLAGE ( )
print mail
```

but generate the following message:

```text
<Cata.cata.maillage_sdaster object at 0x593cad0>
```

There is one exception to this rule: the tables. A programming device makes it simple to retrieve information held in a TABLE data structure by handling it as a two-entry array:

to print a value: print resu[ ‘DX’ , 1] to assign it to a variable: `valeur` = resu[ ‘DX’ , 1]

This of course assumes that the data structure resu, of type TABLE, has already been computed when this instruction is met: so in step-by-step execution mode (PAR_LOT=’NON’).

Lexical remark:

The names of result objects must not exceed 8 characters. Alphanumeric characters are allowed (lowercase and uppercase letters, and digits not in first position), as is the underscore ‘_’. Case matters: the result objects «MAIL» and «Mail» can be used in the same command file and are considered different… this is, however, not advised for the readability of the file!

### 3.3 Possible operations

The command language is structured as a linear sequence of instructions. Besides Python instructions other than Aster commands, which are not discussed for now, three kinds of instructions (or commands) are available:

- the operator, which performs an action and supplies a produced result object of a predefined type, usable by the following instructions of the command set,
- the procedure, which performs an action but supplies no result object,
- the macro-command, which generates a sequence of instructions of the two previous types and can produce zero, one or more result objects.

<!-- page 8 -->

Typically, an operator is an assignment or solution command, and a procedure is a print command (to a file).

From the syntax point of view, an operator has the form:

```text
nomconcept = opérateur( arguments . . . )
```

Whereas a procedure has the form:

```text
procédure( arguments . . . )
```

The syntax of an operator or a procedure is described in the next paragraph.

### 3.4 Rules on the result object produced by an operator

#### 3.4.1 Basic principle

Each time an operator is executed, it supplies a new produced result object of the type predefined in the command catalog.

The result objects that appear as input arguments of the commands are not modified.

#### 3.4.2 Produced result object and reused result object

A reused result object is a result object that, having been produced by an operator, is modified by a new occurrence of this operator or by another operator. A reused result object can be used, as an exception to the Basic Principle, only under two conditions:

- permission given, by the catalog and the programming of the command, to use reusable result objects for the operator: the attribute reentrant of the catalog is ‘o’ or ‘f’,
- explicit request by the user to reuse a produced result object, with the attribute `reuse=nom_du_concept` in the arguments of the commands that allow it.

#### 3.4.3 Checks made by the supervisor on the produced result objects

- Produced result object following the basic principle: The supervisor checks that the name of the produced result object is not already assigned by one of the previous commands, in particular by a command of a previous run in the case of a POURSUITE or an INCLUDE.
- Result object used in reuse: The supervisor checks that:
  - the name of the produced result object is indeed already assigned.
  - the operator is indeed allowed to accept reused result objects,
  - the type of the result object conforms to the type of result object produced by the operator.

Commented examples:

```text
DEBUT ( )
```

| `concept=opérateur ( )` | # (1) | is correct: the result object is defined, |
|---|---|---|
| `concept=opérateur ( )` | # (2) | is incorrect: an attempt is made to redefine the |
| # | result object but without saying so, |   |
| `concept=opérateur (reuse = concept )` # (3) | is correct, if the operator accepts |   |
| # | existing result objects and if the type is |   |
| # | consistent; it is incorrect if the operator |   |
| # | does not accept them. |   |

```text
FIN ( )
```

<!-- page 9 -->

In fact a result object can be created only once: that is, appear to the left of the sign = (equal) without reuse being used in the arguments of the command.

In the case of a reuse, giving the name of the result object again after the attribute reuse is redundant; all the more so since the supervisor checks that the two result object names are identical.

Remark:

A result object can be destroyed, and its name then reused.

### 3.5 Body of a command

#### 3.5.1 Introduction

The body of a command holds the "variable" part of the command. The declarations are separated by commas and, apart from the attribute reuse mentioned above, they all have the form:

```text
[mot_clé]= [argument]
```

The keyword must be a keyword of the current command, declared in its catalog.

#### 3.5.2 Keyword

A keyword is a formal identifier: the name of the attribute that receives the argument.

Example: MATRICE = ...

Syntax remarks:

- the order in which the keywords appear is free; it is not imposed by the order of declaration in the catalogs,
- keywords cannot exceed 16 characters (but only the first 10 characters are significant).

There are two types of keywords: simple keywords and factor keywords, which differ by the nature of their arguments.

#### 3.5.3 Argument of a simple keyword

##### 3.5.3.1 The type of the arguments

The basic types recognized by the supervisor are:

- integers,
- reals,
- complexes,
- texts,
- logicals,
- result objects,
- and the lists of these basic types.

Integers and reals correspond exactly to the equivalent types in Python.

- Optional simple keyword expecting a real:

```text
Catalogue          :  VALE   = SIMP( statut=’f’ , typ = ‘R’ ) ,
```

Command file: VALE = 10. ,

- Optional simple keyword expecting an integer:

```text
Catalogue          :  INFO   = SIMP( statut=’f’ , typ = ‘I’ ) ,
```

Command file: INFO = 1 , The complex type is represented by a Python "tuple" holding a character string that gives the representation mode of the complex number (real and imaginary parts, or modulus-phase) followed by the numerical values.

<!-- page 10 -->

```text
Catalogue              :  VALE_C = SIMP( statut=’f’ , typ = ‘C’ ) ,
```

| Command file | : | VALE_C = ( ‘RI’ , 0.732 , -0.732 ) , |
|---|---|---|
| Command file | : | VALE_C = ( ‘MP’ , 1. , -45. ) , |

The two notations are strictly equivalent. In the ‘MP’ notation, the phase is in degrees.

The text type is declared between single quotes. Case is respected. However, when a keyword must take a value from a list predefined in the catalog, the convention today is that this value is always in capitals.

```text
Catalogue           :  TOUT   =SIMP( typ=‘TXM’,into=(‘OUI’,’NON’)) ,
```

Command file: TOUT = ‘OUI’ ,

Case matters and, in the context above, the following command line will fail:

Command file: `TOUT = ‘oui’` ,

The logical type is not used today in the command catalog.

A result object is declared simply by its name, without single or double quotes.

##### 3.5.3.2 Notion of list

Caution:

The word «list» is a misuse of language here. It is not the Python «list» type but rather tuples, in the Python sense: the items are declared between an opening and a closing parenthesis; they are separated by commas.

Lists are homogeneous lists, that is, their items are of the same basic type. Any basic type can be used in a list.

Examples of lists: list of integers (1, 2, 3, 4),

```text
listedetexte     ( 'ceci', 'est', 'une', 'liste', 'de', 'texte'),
```

list of result objects ( resu1, resu2, resu3 ),

Ease of use:

A list reduced to one item may be written without parentheses.

Example of a wrong list:

Heterogeneous list of integer and real

```text
(1, 3, 4.)
```

#### 3.5.4 Factor keyword

Some information cannot be given globally (once in the command), so it is important to allow some keywords to be repeated, to assign them different arguments. The factor keyword offers this possibility; under a factor keyword there is a set of (simple) keywords that can be used at each occurrence of the factor keyword. This also improves the readability of the command file by grouping keywords that share a common meaning: for example the different parameters of one material.

<!-- page 11 -->

Unlike the simple keyword, the factor keyword can receive only one type of object: the supervisor object «_F», or a list of it.

Either the factor keyword has only one occurrence and one can write, for example, either:

```text
IMPRESSION   =      _F(RESULTAT =   resu,  UNITE = 6),
```

or

```text
IMPRESSION   =  (   _F(RESULTAT =   resu,  UNITE = 6), ),
```

In the first case, the factor keyword IMPRESSION receives an object _F; in the other, it receives a singleton. Mind the comma: in Python, a one-item tuple is written (item,)

Or the factor keyword has several occurrences, two in this example:

```text
IMPRESSION   =  (   _F(RESULTAT =   resu1, UNITE = 6),
                    _F(RESULTAT =   resu2, UNITE = 7)   ),
```

The expected number of occurrences (minimum and/or maximum) of a factor keyword is defined in the command catalog.

Notion of default value

The supervisor can assign default values. These values are defined in the command catalog and not in the FORTRAN.

From the point of view of the routine associated with the command, there is no distinction between a value given by the user and a default value introduced by the supervisor. This appears when the supervisor prints the user commands in the message file: all the default values appear in the command text, if they were not given by the user

Reminder: a result object cannot be given a default value.

## 4 Defining values and evaluating expressions

Values can be assigned to Python variables so as to use them as arguments of simple keywords: these variables are called parameters in EFICAS. They can hold integer, real or complex values, texts, or lists of these types.

Example:

```text
young =   2.E+11
mat   =   DEFI_MATERIAU( ELAS = _F(  E = young , NU = 0.3 ) )
```

At the end of the run, the Python context is saved with the database. So in the continuation that follows, the parameters are still present, with their predefined values, just like the ASTER result objects.

Python operations can be performed on the arguments of simple keywords:

```text
Pisur2=   pi/2.
mat   =   MA_COMMANDE  ( VALE = Pisur2 )
```

or:

```text
var   =   ’ world’
mat   =   MA_COMMANDE  (  VALE   = pi/2. ,
                          VALE2  = Pisur2+cos(30.) ,
                          TEXTE  = ‘hello’+var   )
```

## 5 Using Python in command files

Knowing the Python language is not necessary to use Code_Aster. Indeed, provided a few basic rules on indentation and parentheses are followed, only knowledge of the command language described in the command catalogs is needed. And even then, EFICAS removes the need to consult the catalog or the «syntax» paragraph of the commands by offering graphically the keywords to fill in.

However, the advanced user can make good use of the power of the PYTHON language in the command file, since the file is already written in this language.

The four main uses can be: writing custom macro-commands, using general Python instructions, importing useful Python modules, and retrieving information from Code_Aster data structures into PYTHON variables.

Remark:

To use accented French characters in the command file or in the imported modules, the following instruction must be placed on the first or second line of the file:

```text
# –*– coding: iso–8859–1 –*–
```

In Python 2.3, the absence of this line causes a warning that becomes an error in Python 2.4; in ASTER, it is always an error.

### 5.1 Custom macro-commands

See document [D5.01.02]: «Introducing a new macro-command». Custom macro-commands are very easy to program. They can be used to capture recurring calculation schemes and so build a domain tool. It is strongly advised to follow the example of the existing macro-commands: package Macro in the directory bibpyt.

### 5.2 General PYTHON instructions and useful modules

Advanced users can benefit greatly from using loops (for), tests (if), exceptions (try, except) and, in general, the full power of the PYTHON language directly in their command file. An exhaustive list of uses cannot be drawn up. Many examples are present in the test cases of the test base. For example, mesh adaptation can be done by placing the calculation/remeshing sequence in a loop, and a stop criterion for the iterations can be set by a test on a computed value.

See the next paragraph, on «customized» Aster exceptions.

In a loop, if an already existing result object is re-created, remember to destroy it first with the command DETRUIRE.

Other miscellaneous Python features of interest to the Code_Aster user can be:

- reading and writing files,
- numerical computation (for example with Numerical Python),
- calling the scripting language through the module os, and in particular launching a third-party code (os.system)
- handling character strings
- calling graphics modules (grace, gnuplot)

### 5.3 PYTHON exceptions of the module aster

<!-- page 13 -->

The Python exception mechanism is very useful: it allows, for example, «trying» a command and then taking back control if the command «crashes» by raising a particular exception:

```text
try:
    bloc d’instructions
except ErreurIdentifiée, message:
    bloc d’instructions exécuté si ErreurIdentifiée se produit…
```

In the command file, this mechanism can be used with any exception of the standard Python modules. There are also exceptions specific to Code_Aster (in the module aster), in two categories: the exceptions associated with <S> errors, and the one associated with <F> errors.

#### 5.3.1 Catching <S> errors

In case of an <S> error, the error is identified by one of these exceptions:

| aster.NonConvergenceError | if the calculation does not converge, |
|---|---|
| aster.EchecComportementError | problem during the integration of the constitutive law, |
| aster.BandeFrequenceVideError | no mode found in the frequency band, |

```text
aster.MatriceSinguliereError           m atricesingulière,
```

| aster.TraitementContactError | problem during contact processing, |
|---|---|
| aster.MatriceContactSinguliereError | singular contact matrix, |
| aster.ArretCPUError | stop for lack of CPU time. |

All these exceptions derive from the general <S> exception, aster.error. This means that except aster.error catches all the exceptions listed above. It is nevertheless always better to state which error is expected!

Example of use:

```text
try:
    resu = STAT_NON_LINE(...)
except aster.NonConvergenceError, message:
    print ‘Arrêt pour cette raison : %s’ % str(message)
    # On sait qu’il faut beaucoup plus d’itérations pour converger
    print "On continue en augmentant le nombre d’itérations."
    resu = STAT_NON_LINE(reuse = resu,
                         ...,
                         CONVERGENCE=_F(ITER_GLOB_MAXI=400,),)
except aster.error, message:
```

#### 5.3.2 Catching <F>atal errors

In case of a fatal error, the behavior can be changed by the user. By default, the code stops with an <F> error, and the error traceback (calls of the Fortran routines) can be seen in the output file. If desired, the code can raise the exception aster.FatalError; in that case (as for an <S> error), if the exception is caught by an except, the user takes back control, otherwise the code stops (no Fortran error traceback). This choice is set in the commands DEBUT/POURSUITE, factor keyword ERREUR (see [U4.11.01] and [U4.11.03]), and at any time by the method aster.onFatalError.

<!-- page 14 -->

Called without argument, this method returns the current behavior in case of a fatal error:

```text
comport = aster.onFatalError()
print "Comportement courant en cas d’erreur fatale : %s” % comport
```

and it sets the desired behavior:

```text
aster.onFatalError(‘EXCEPTION’)   #on lèvel’exceptionFatalError
```

or aster.onFatalError(‘ABORT’) # stop with error traceback.

#### 5.3.3 Validity of result objects when an exception is raised

When an exception is raised and caught (by except), the result object produced by the command in which the error occurred is returned as it is, since the command did not end normally. In some cases, especially after a fatal error, the produced result object may not be usable; then use DETRUIRE to delete it. Likewise, to reuse the name of the result object to create a new one, DETRUIRE the one obtained in the try.

For <S> errors raised in STAT/DYNA_NON_LINE, the result object is generally valid and can be reused (keyword reuse) to continue the calculation with another strategy (as in the example given earlier).

Finally, before control is returned to the user, the objects of the volatile database are deleted by a call to JEDETV, and the Jeveux mark is reset to 1 (with JEDEMA) to free the objects brought into memory.

#### 5.3.4 Precautions for using exceptions

The two exceptions aster.error and aster.FatalError are independent (neither derives from the other), which means that to take back control in case of an <S> error and an <F> error:

<!-- chunk 10 fr=d09dce589255 method=machine source=session:task-5.2 on=2026-10-30 -->

- raising the exception in case of an <F> error must be activated with aster.FatalError(‘EXCEPTION’) or in DEBUT/POURSUITE.
- both exceptions must be caught:

```text
except (aster.FatalError, aster.error), message:  …
```

Using «except:» without stating which exception is expected is not advised (this is a general rule in Python, independent of the Aster exceptions). Indeed, the processing done under the except is unlikely to be valid for every error case.

Likewise, as in the example given above, it is better to use the customized exceptions NonConvergenceError, ArretCPUError, … than the higher-level exception aster.error; again, so as to know exactly what happened.

### 5.4 Retrieving computed values into PYTHON variables

Using the PYTHON language in a command file is useful only if actions can be launched conditionally, depending on what the code has computed.

Some bridges exist between Python and the data structures computed by the code and present in the JEVEUX memory. Others remain to be programmed; this is an evolving area and future developments are expected.

It is essential to understand that retrieving computed data requires the instructions that produce them to have actually been executed beforehand. In other words, the code must be run in mode PAR_LOT=’NON’ (keyword of the command DEBUT). Indeed, in this case there is no global analysis of the command file; each instruction is executed sequentially.
