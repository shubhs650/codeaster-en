# CALC_CHAMP operator

## 1 Purpose

Create or complete a result by computing element or nodal fields (stresses, strains, …).

The result object produced is either created or modified; that is, CALC_CHAMP is called as follows:

```text
r esu = CALC_CHAMP  (  RESULTAT = resu … ,  reuse = resu , … )
```

or

```text
resu1 = CALC_CHAMP  (  RESULTAT = resu, … )
```

### 2.1 Operands RESULTAT/MODELE/CHAM_MATER/CARA_ELEM/EXCIT

#### 2.1.1 Operands RESULTAT

```text
♦  RESULTAT =   resu
```

Name of the result data structure to enrich. This argument can be the same as the one used for the object enriched by the operator, or a different name, which creates a new result data structure.

Remarks:

- In most situations, the data structure resu holds all the information needed to compute the options: the model, the material field, the element properties, the loads. The keywords MODELE , CHAM_MATER , CARA_ELEM and EXCIT are therefore not needed;
- A notable exception, however, is the dynamic data structures from DYNA_VIBRA, for which the user must make sure the keywords are consistent between the calculation operator and CALC_CHAMP . A warning says so.

#### 2.1.2 Operands MODELE / CHAM_MATER / CARA_ELEM.

```text
◊  MODELE = mo
```

Name of the model on which the forces, stresses, strains, etc. are computed. It is optional because it can be taken from the result.

```text
◊  CHAM_MATER = chmater
```

Material field associated with the model mo. This keyword is optional and should only be given in exceptional cases (deliberate change of the material, for example).

```text
◊  CARA_ELEM = carac
```

Element properties associated with the model mo if it holds structural elements or if the isoparametric elements are assigned a local anisotropy coordinate system. This keyword is optional because it can be taken from the result.

#### 2.1.3 Keyword EXCIT

This (optional) factor keyword gives the thermal or mechanical loads to use for computing the options, in place of those used in the calculation of the data structure given under the keyword RESULTAT.

This keyword is defined in the same way as in the commands that built the data structure resu: see the commands MECA_STATIQUE [U4.51.01], STAT_NON_LINE [U4.51.03], DYNA_VIBRA [U4.53.03].

### 2.2 Selecting the elements concerned by the calculation

The keywords TOUT and GROUP_MA let the user choose the elements on which the elementary post-processing calculations are done.

```text
/  TOUT = 'OUI'
```

All the elements (carrying finite elements) are processed. This is the default value.

```text
/  GROUP_MA  =  l_grma
```

Only the elements in l_grma are processed.

### 2.3 Selecting the step indices

The use of the keywords TOUT_ORDRE, NUM_ORDRE, INST,FREQ is described in the document [U4.71.00]. When there are many step indices, it can be more efficient (in memory especially) to call the command several times on sub-lists of the step indices.

### 2.4 Location of the fields

In the rest of the document, the location of the fields is not stated explicitly, because it is given in the name of the field (and therefore of the option):

- Field per element: *_ELEM
- Element field at Gauss points: *_ELGA
- Element field at element nodes: *_ELNO
- Nodal field: *_NOEU

Most fields are computed natively at the Gauss points (*_ELGA).

The fields at element nodes (*_ELNO) are obtained by extrapolation from the field at the Gauss points (method detailed in [R3.06.03]).

The nodal fields (*_NOEU) are obtained from the fields at element nodes by a simple arithmetic mean (not weighted by element size) of the values met on the elements at a given node.

Remark 1: For equivalent quantities, the fields at element nodes (*_ELNO) are not obtained by extrapolation from the field at the Gauss points. The extrapolation is done on the stress or strain field, and the equivalent field is then computed.

Remark 2: Nodal averages of fields computed in local coordinate systems are only valid if the angles between these coordinate systems are small. Otherwise they have no meaning.

Remark 3: When the keyword GROUP_MA is given for the calculation of a *_NOEU option, the arithmetic mean is taken over the selected elements. This result therefore differs from the one obtained by a global calculation then restricted to the selected elements. Example: Consider a structure whose shear stress  is: xy <!-- equation -->

For structural elements that have sub-points (plates, shells, multifiber beams, pipes), the fields of type *_ELGA and *_ELNO are computed on all the sub-points. To get a field on a single sub-point (one layer and one level, for example), extract it with the operator POST_CHAMP (options EXTR_COQUE, EXTR_PMF and EXTR_TUYAU). This intermediate operation is in fact essential to compute a field of type *_NOEU for these structural elements: fields of type *_NOEU never have sub-points.

Finally, the energy calculation options never produce fields with sub-points. For structural elements, the field is integrated through the thickness (integration over the sub-points).

### 2.5 Field dependencies

Computing a field may need one or more other fields to be computed first. For example, to compute a *_NOEU field, the same field at element nodes *_ELNO and at Gauss points *_ELGA is needed.

The operator CALC_CHAMP resolves this dependency by computing the intermediate fields automatically. The user therefore does not need to know the dependency tree of the options. Only the fields explicitly requested by the user are saved in the result data structure.

### 2.6 Operands for the mechanical options

#### 2.6.1 Stress calculation options (Operand CONTRAINTE)

The components of the stress and generalized force fields are detailed in the document [U2.01.05].

```text
|  'EFGE_ELGA'
|  'EFGE_ELNO'
|  'EFGE_NOEU'
```

Calculation of the generalized forces (structural elements).

This is either an extraction of the forces held in the field SIEF_ELGA/STRX_ELGA (for beam/pipe elements or discrete elements), or a calculation by integration of the stresses (for multifiber beam elements or plates and shells).

Remark 1: The field EFGE_ELNO is not always an extrapolation of the field EFGE_ELGA; in particular, for a linear calculation this field is computed directly from the displacement. This is why some components are not computed (set to zero) in nonlinear analysis.

Remark 2: For offset plates, the forces are computed in the «plane» of the mesh. To get these forces in the mean «plane» of the plate, use the command POST_CHAMP / COQUE_EXCENT.

```text
|  'SIEF_ELGA'
|  'SIEF_ELNO'
|  'SIEF_NOEU'
```

This component is computed from the trace of the stresses (part of the constitutive law) and from the unknowns PRES and GONF (for INCO_UPG) of the nodal unknowns field. Using GROUP_MA in FORC_NODA and REAC_NODA

If the keyword GROUP_MA is given, F (option FORC_NODA) is computed only on the requested elements K and then assembled. The result differs from a global calculation over the whole domain then reduced to the requested elements. The method implemented measures the reaction of one part of the model on another. <!-- equation -->

Warning! The calculation of 'REAC_NODA' on a subset of the model (through the keyword GROUP_MA) must be done with care. Example 4 below illustrates this type of calculation.

For results of type `dyna_harmo` , 'REAC_NODA' is computed only on the whole model. The calculation on a subset of the model can be done by hand by computing 'FORC_NODA' on the element group concerned and then subtracting the external force from the results obtained.

Remarks:

- The nodal reactions are zero at every interior point of the model and are not zero a priori at a boundary point subjected to a kinematic boundary condition (or to contact forces);
- Neglecting the contribution of damping in dynamics can create a small deviation from the exact result;
- Only the resultant of the nodal forces or reactions over a node group has a physical meaning (this group must correspond to at least one element of the model, for example a boundary subjected to a boundary condition). It can be computed with POST_RELEVE_T [U4.81.21] . Pointwise, the field FORC_NODA or REAC_NODA must not be interpreted, because the value at a node depends directly on the mesh refinement. Also, the sign of these forces on the nodes of one element can be counter-intuitive while being fully consistent with finite element theory (for example on QUAD8 elements at the interface of a zone in pure compression, the signs of the nodal forces at the corners and at the middles are opposite);
- The calculation of REAC_NODA takes into account the distributed loads on beams. As soon as this load varies in a nonlinear calculation (change of EXCIT from one time step to the next), the calculation of REAC_NODA is forbidden. The post-processing must then be split into «batches» of step indices for which the load is constant (that is, it uses the same AFFE_CHAR_MECA object in EXCIT).
- Some loads are not taken into account when computing this option: INTE_ELEC, FORCE_SOL and RELA_CINE_BP.

### 2.10 Calculation of a user field

The factor keyword CHAM_UTIL computes arbitrary fields, called «user» fields because of the name they are given in the result object. CHAM_UTIL can have several occurrences, to chain the calculation of several fields. Since the processing is done at the end of the command CALC_CHAMP, the fields computed by the previous keywords (CONTRAINTE, DEFORMATION...) are available here. Either a predefined criterion is requested, or one or more formulas are applied to compute another field.

#### 2.10.1 Operand NOM_CHAM

The field from which the calculations are done. The field produced has the same type: ELGA, ELNO or NOEU.

#### 2.10.2 Operand CRITERE

Requests the calculation of a predefined criterion. The criteria are (section 2.6.5 gives the expression of each criterion):

- VMIS (for stress fields),
- INVA_2 (for strain fields),
- TRACE (for stress or strain fields).

Each of these criteria produces one component (named X1). One benefit is that INVA_2 can be computed for any strain field.

#### 2.10.3 Operand FORMULE

This computes any expression that is a function of the components of the field given for NOM_CHAM. The field produced holds as many components as formulas given: the first formula gives the component X1, the second X2, etc. Up to 30 components can be created this way. The output field is always extended with zero on the other components and where the input field is not defined.

Examples of formulas that reproduce the criteria VMIS and INVA_2 can be found in the second part of the test sslv104a.

- L2 : L norm of a tensor 2

### 2.13 Calculation performance: parallelism in space or in time?

◊ PARALLELISME_TEMPS = ‘OUI’/’NON’ [DEFAUT] (active only for the options REAC/FORC_NODA and ***_NOEU).

By default, when MPI parallelism is enabled1 (see [U2.08.06]), the calculation options generally use parallelism «in space». That is, the calculations are distributed over the parallel processes by batches of elements. An MPI process handles, for all the time steps, the elementary calculations needed by a given element group. But besides being inefficient for options that involve few or no elementary calculations directly (such as the options REAC/FORC_NODA and ***_NOEU ), this parallelism also causes large and repeated MPI communications2 .

For the options above, parallelism «in time» is therefore preferred: it distributes, for all the elements, the calculations (elementary or not) needed by a batch of time steps. Communications are therefore cheaper3 and the parallelism extends to parts of the code beyond the elementary calculations. With this parallelism, speedups can range from X5 to X50 depending on the configuration of the calculations. This parallelism is enabled in a given CALC_CHAMP4 and applies to all the calculation options that can benefit from it: REAC/FORC_NODA and ***_NOEU and all the underlying calculation options5 . For an expensive CALC_CHAMP with REAC/FORC_NODA or ***_NOEU calculations over long transients and/or on large models, enabling this parallelism in time is therefore recommended: PARALLELISME_TEMPS=’OUI’. And, unlike parallelism in space, it does not need a minimum granularity6 to be efficient. From about ten time steps per MPI process, the speedup from parallelism in time can be significant7.

The type of parallelism active (in space, in time or none) is given, option by option, in the message file. For more details, see the user notice on parallelism [U2.08.06].

Remarks on parallelism:

- Parallelism in time, when enabled in the operator, applies to all the processing that can benefit from it. To do so, parallelism in space is «switched off» behind the scenes and temporarily, option by option. It is then re-enabled, «as if nothing had happened», in the following options if they are not themselves concerned by parallelism in time. Thus the call

```text
CALC_CHAMP(EFGE_ELGA, REAC_NODA, ETOT_ELGA, EPSI_NOEU,
    PARALLELISME_TEMPS=’OUI’)
```

enables parallelism in space for options no. 1 and no. 3 and parallelism in time for the others . From the parallelism point of view, it is equivalent to the sequence of calls:

```text
CALC_CHAMP(EFGE_ELGA, ETOT_ELGA)
CALC_CHAMP(REAC_NODA, EPSI_NOEU, PARALLELISME_TEMPS=’OUI’)
```

- To keep the programming simple8 and not chase minor gains needlessly, when the number of time steps is not a multiple of the number of MPI processes, the remaining time steps are done by all the processes. And of course no communication is organized between them.
